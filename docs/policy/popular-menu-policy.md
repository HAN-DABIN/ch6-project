# Popular Menu Policy

인기 메뉴 정책은 최근 주문 데이터를 기준으로 메뉴 랭킹을 정확하고 빠르게 제공하기 위한 기준이다.
정확한 주문/결제 데이터의 원천은 MySQL이고, Redis는 조회 성능 개선을 위한 랭킹 캐시로 사용한다.

## 기본 규칙

- 인기 메뉴는 최근 7일간 주문된 메뉴를 기준으로 집계한다.
- 인기 메뉴는 주문 횟수가 많은 순서로 최대 3개를 조회한다.
- 주문 횟수가 같은 경우 정렬 기준은 별도 정책으로 정한다.
- 결제가 완료된 주문만 인기 메뉴 집계 대상이다.
- 취소되거나 실패한 주문은 집계 대상에 포함하지 않는다.

## 데이터 원천 규칙

- 주문과 결제의 진실의 원천은 MySQL이다.
- Redis에 저장된 랭킹 데이터는 조회 성능 개선을 위한 캐시 데이터다.
- Redis 데이터가 유실될 수 있으므로 필요한 경우 MySQL 주문/결제 데이터로 재집계할 수 있어야 한다.

## Redis ZSET 규칙

- Redis ZSET을 사용해 날짜별 메뉴 주문 횟수를 저장한다.
- key는 날짜 단위로 관리한다.
- value는 메뉴 ID를 문자열로 저장한다.
- score는 해당 날짜의 주문 횟수로 저장한다.
- 주문 결제 완료 이벤트를 소비하면 해당 날짜 key의 메뉴 score를 1 증가시킨다.

## 최근 7일 조회 규칙

- 인기 메뉴 조회 시 오늘을 포함해 최근 7일의 Redis ZSET key를 조회한다.
- 7일간의 날짜별 score를 메뉴 ID 기준으로 합산한다.
- 합산 결과를 주문 횟수 내림차순으로 정렬한다.
- 상위 3개의 메뉴를 응답한다.

## 메뉴 정보 조회 규칙

- Redis 랭킹에는 메뉴 ID와 주문 횟수만 저장한다.
- 메뉴 이름, 가격, 상태 같은 상세 정보는 메뉴 데이터에서 조회한다.
- 인기 메뉴 조회 시 메뉴별 개별 `findById` 반복 조회는 피한다.
- 상위 메뉴 ID 목록을 구한 뒤 `findAllById`로 bulk 조회하는 방식을 우선 고려한다.
- 메뉴 상세 정보까지 Redis에 캐싱하는 방식은 조회 성능을 더 높일 수 있지만, 메뉴 정보 변경 시 캐시 무효화 정책이 필요하므로 2차 고도화로 둔다.

## Kafka 연동 규칙

- 주문 결제가 완료되면 `PaymentCompletedEvent`가 발행된다.
- 인기 메뉴 Consumer는 `PaymentCompletedEvent`를 소비해 Redis ZSET 랭킹을 갱신한다.
- Consumer는 이벤트의 실제 필드만 사용해야 한다.
- 이벤트 처리 실패 시 재처리 또는 보정 집계 방안을 고려해야 한다.

## 일관성 규칙

- Redis 랭킹은 빠른 조회를 위한 데이터이므로 MySQL과 일시적으로 차이가 날 수 있다.
- 최종적인 주문/결제 기록은 MySQL을 기준으로 판단한다.
- 랭킹 정확성이 중요한 경우 MySQL 기반 재집계 작업을 별도로 둘 수 있다.

## 실패 처리 규칙

- 인기 메뉴 데이터가 없으면 빈 배열을 반환한다.
- Redis에 특정 날짜의 랭킹 데이터가 없어도 전체 조회가 실패하면 안 된다.
- Redis 장애 시 대체 조회 전략을 둘지 여부는 별도 고도화 정책으로 정한다.
