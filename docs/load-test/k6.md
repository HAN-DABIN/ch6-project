# k6 Load Test Guide

이 문서는 현재 코드 기준으로 메뉴 조회 API와 Redis ZSET 기반 인기 메뉴 조회 API의 응답 특성을 비교하기 위한 k6 실행 방법을 기록한다.

## 대상 API

| 구분 | Method | Path | 인증 | 비교 관점 |
| --- | --- | --- | --- | --- |
| 메뉴 조회 | GET | `/api/menus` | 불필요 | MySQL `menus` 전체 조회 |
| 인기 메뉴 조회 | GET | `/api/menus/popular` | 불필요 | Redis 최근 7일 ZSET 합산 + MySQL 메뉴 bulk 조회 |

이번 부하 테스트는 캐시 전/후 비교가 아니다. 현재 코드에는 인기 메뉴를 매번 MySQL 원본 집계로 조회하는 API와 Redis ZSET으로 조회하는 API가 동시에 존재하지 않는다. 따라서 일반 메뉴 조회와 인기 메뉴 조회라는 현재 구현된 두 조회 전략의 latency, 실패율, 처리량을 비교한다.

## 스크립트

- `k6/menu-read-test.js`

지원 시나리오:

| `K6_SCENARIO` | 설명 |
| --- | --- |
| `smoke` | 낮은 부하로 응답 계약과 스크립트 동작을 확인한다 |
| `menus` | `GET /api/menus`만 호출한다 |
| `popular` | `GET /api/menus/popular`만 호출한다 |
| `mixed` | 메뉴 조회 70%, 인기 메뉴 조회 30% 비율로 호출한다 |

기본값:

- `BASE_URL`: `http://localhost:8080`
- `K6_SCENARIO`: `mixed`
- `K6_VUS`: `10`
- `K6_DURATION`: `1m`

## 사전 준비

1. 애플리케이션을 실행한다.

```bash
./gradlew bootRun
```

2. 애플리케이션이 사용하는 MySQL과 Redis가 실행 중인지 확인한다.
3. 메뉴 조회 결과를 의미 있게 보려면 `menus` 데이터가 있어야 한다.
4. 인기 메뉴 조회 결과가 빈 배열이 아닌 상태를 보려면 Redis에 날짜별 ZSET 데이터가 있어야 한다.

Redis seed 예시:

```bash
redis-cli ZADD menu:ranking:2026-07-19 30 1 20 2 10 3
```

날짜는 테스트 실행일에 맞게 바꾼다. 현재 구현은 오늘을 포함해 최근 7일 key를 조회한다.

## 실행 방법

smoke:

```bash
BASE_URL=http://localhost:8080 K6_SCENARIO=smoke k6 run k6/menu-read-test.js
```

메뉴 조회 단독:

```bash
BASE_URL=http://localhost:8080 K6_SCENARIO=menus K6_VUS=10 K6_DURATION=1m k6 run k6/menu-read-test.js
```

인기 메뉴 조회 단독:

```bash
BASE_URL=http://localhost:8080 K6_SCENARIO=popular K6_VUS=10 K6_DURATION=1m k6 run k6/menu-read-test.js
```

혼합 조회:

```bash
BASE_URL=http://localhost:8080 K6_SCENARIO=mixed K6_VUS=10 K6_DURATION=1m k6 run k6/menu-read-test.js
```

## checks

스크립트는 각 API에 대해 다음을 확인한다.

- HTTP status가 `200`인지 확인
- 공통 응답 `status`가 `200`인지 확인
- 응답 메시지가 실제 Controller 메시지와 일치하는지 확인
  - 메뉴 조회: `메뉴 조회 성공`
  - 인기 메뉴 조회: `인기 메뉴 조회 성공`
- `data`가 배열인지 확인

## thresholds

초기 기준은 다음과 같이 둔다.

- 전체 check 성공률: `checks > 99%`
- 전체 HTTP 실패율: `http_req_failed < 1%`
- 메뉴 조회 HTTP 실패율: `http_req_failed{api:menus} < 1%`
- 인기 메뉴 조회 HTTP 실패율: `http_req_failed{api:popular-menus} < 1%`
- 메뉴 조회 p95: `http_req_duration{api:menus} p95 < 1000ms`
- 인기 메뉴 조회 p95: `http_req_duration{api:popular-menus} p95 < 1000ms`

p95 목표값은 로컬 장비 성능, Docker 상태, MySQL/Redis 데이터 크기에 따라 달라질 수 있으므로 최초 안정 실행 결과를 기준선으로 남긴 뒤 조정한다.

## 결과 해석

- `http_req_duration{api:menus}`는 MySQL 메뉴 조회의 응답 시간을 본다.
- `http_req_duration{api:popular-menus}`는 Redis 최근 7일 ZSET 조회와 MySQL 메뉴 bulk 조회가 결합된 응답 시간을 본다.
- 인기 메뉴 데이터가 비어 있으면 Redis key 조회 후 빈 배열을 반환하므로, 랭킹 데이터가 있는 상태와 없는 상태를 구분해 기록한다.
- 두 API 모두 인증이 필요 없으므로 JWT 발급 비용은 포함하지 않는다.

## 주문/결제 부하 테스트 방향

`POST /api/orders`는 이번 스크립트에 포함하지 않는다.

이유:

- JWT 인증이 필요하다.
- 테스트 사용자별 충분한 포인트 잔액이 필요하다.
- 같은 사용자를 반복 사용하면 비관적 락 경합을 측정하게 된다.
- Kafka `payment-completed` topic, Redis, MySQL 상태가 모두 결과에 영향을 준다.

후속 작업에서는 주문 테스트를 두 흐름으로 분리하는 것이 좋다.

- 정상 주문 처리량: 여러 사용자와 충분한 포인트를 준비해 락 경합을 낮춘다.
- 동일 사용자 동시 주문: 의도적으로 같은 사용자 포인트 row에 락 경합을 만들고 중복 차감 방지 특성을 본다.

## 남은 리스크

- k6가 로컬에 설치되어 있지 않으면 스크립트 실행은 불가능하다.
- Redis 인기 메뉴 seed가 없으면 인기 메뉴 API는 정상이어도 빈 배열 중심으로 측정된다.
- Redis 장애나 Kafka 이벤트 누락으로 랭킹 데이터가 MySQL 원천 데이터와 다를 수 있다.
- 이 문서는 부하 테스트 실행 방법을 제공하지만, 운영 수준의 성능 기준은 별도 환경에서 반복 측정해 정해야 한다.
