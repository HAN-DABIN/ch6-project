# Code Convention

이 문서는 `ch6-project`의 코드 작성 기준을 기록한다.
Agent는 코드를 생성하거나 수정하기 전에 이 문서를 확인한다.

## 기본 원칙

- 기존 패키지 구조와 네이밍을 우선한다.
- Controller, Service, Repository, Entity, DTO의 책임을 섞지 않는다.
- 요구사항과 무관한 리팩터링은 하지 않는다.
- 존재하지 않는 클래스, 메서드, 필드를 있다고 가정하지 않는다.
- 공통 응답, 예외, 인증 방식은 기존 구현을 먼저 확인한 뒤 따른다.

## 계층별 기준

### Controller

- HTTP 요청과 응답 변환에 집중한다.
- 비즈니스 판단은 Service로 위임한다.
- 응답 형식은 `CommonApiResponse`를 사용한다.
- 인증 사용자가 필요한 경우 기존 Security/JWT 흐름을 따른다.

### Service

- 비즈니스 로직과 트랜잭션 경계를 담당한다.
- 주문, 결제, 포인트 차감처럼 원자성이 필요한 작업은 하나의 트랜잭션 안에서 처리한다.
- 외부 시스템 Kafka, Redis와의 일관성 처리 방식을 코드 또는 문서에 남긴다.

### Repository

- 데이터 조회와 저장 역할만 담당한다.
- 반복 조회가 예상되는 경우 bulk 조회를 먼저 고려한다.
- 동시성 제어가 필요한 조회는 잠금 또는 조건부 갱신 전략을 명확히 한다.

### Entity / DTO

- Entity는 영속성 모델과 도메인 상태를 표현한다.
- DTO는 요청/응답 계약을 표현한다.
- Entity를 API 응답으로 직접 노출하지 않는다.

## 예외 처리

- 도메인 오류는 `CustomException`과 `ErrorCode`를 사용한다.
- 예외 메시지는 사용자에게 필요한 수준으로만 노출한다.
- 검증 실패, 인증 실패, 리소스 없음, 잔액 부족은 구분 가능한 에러 코드로 관리한다.

## 테스트 기준

- Service 로직은 단위 테스트 또는 슬라이스 테스트를 우선 고려한다.
- Controller 변경은 요청/응답 계약 검증을 포함한다.
- Redis, Kafka, MySQL이 필요한 검증은 실행 환경 의존성을 기록한다.
